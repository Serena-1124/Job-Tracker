# JobTracker 登录功能设计说明

## 一、为什么必须设置登录功能

### 1. 数据隔离需求
JobTracker 是一款个人数据管理工具，用户的核心诉求是**记录和管理自己的求职数据**。如果不设置登录功能，会出现以下问题：

- **数据混用**：同一台电脑上，用户A使用后退出，用户B登录会看到用户A的数据
- **隐私泄露**：求职信息属于敏感个人信息，包含公司名称、面试进度、薪资等，不应被他人查看
- **同步混乱**：如果不区分用户身份，云端数据无法正确归属，导致数据覆盖或丢失

### 2. 跨设备同步需求
用户的核心场景之一是**跨设备使用**（如公司电脑记录，回家查看）。实现跨设备同步必须满足：

- **身份识别**：云端需要知道"这条数据属于谁"
- **数据归属**：通过 user_id 字段关联数据，确保用户只能访问自己的数据
- **安全隔离**：通过行级安全策略（RLS）防止用户访问他人数据

### 3. 数据持久化需求
如果不设置登录功能，数据只能存储在浏览器本地（IndexedDB），存在以下风险：

- **清理丢失**：用户清理浏览器缓存或Cookie时，数据会被清除
- **换设备丢失**：无法在新设备上恢复数据
- **浏览器限制**：部分浏览器对IndexedDB有存储限制

**登录功能 + 云端同步** 解决了以上所有问题，确保数据安全、持久、可跨设备访问。

## 二、删除游客模式的考量

### 1. 游客模式的问题

早期版本曾设计"游客模式"，允许用户不登录直接使用。但实际使用中发现以下问题：

| 问题 | 说明 |
|------|------|
| **数据无法同步** | 游客数据存储在本地，无法上传到云端 |
| **切换账号困难** | 游客数据与登录数据不互通，切换账号后数据丢失 |
| **数据安全隐患** | 同一浏览器的不同用户共享同一份本地数据 |
| **用户体验割裂** | 游客模式下功能受限（如云同步、跨设备访问不可用） |

### 2. 删除游客模式的决策过程

**方案对比：**

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **A. 强制登录** | 删除游客模式，必须登录才能使用 | 数据隔离清晰、同步逻辑简单、用户体验一致 | 新用户需要注册账号 |
| **B. 保留游客+数据迁移** | 游客数据可迁移到登录账号 | 用户体验平滑 | 迁移逻辑复杂，容易出错 |
| **C. 保留游客+本地隔离** | 游客也按账号隔离本地数据 | 兼顾体验和隔离 | 同步逻辑复杂，云端数据管理困难 |

**最终选择方案A（强制登录）的原因：**

1. **产品定位**：JobTracker 是长期使用的个人工具，用户有动力注册账号
2. **技术简化**：删除游客模式后，代码逻辑大幅简化（无需处理两种模式的数据源切换）
3. **数据安全**：强制登录从根本上解决了数据隔离问题
4. **功能完整**：登录后所有功能（云同步、跨设备、数据导出）均可正常使用
5. **维护成本**：减少模式切换带来的bug和维护成本

### 3. 利弊权衡

**利：**
- 代码逻辑清晰，维护成本低
- 数据隔离彻底，安全性高
- 用户体验一致，无需区分模式
- 同步逻辑简单，可靠性高

**弊：**
- 新用户首次使用需要注册（增加一步操作）
- 无法"先试用再注册"

**权衡结论：** 对于一款数据管理工具，"数据安全"和"功能完整性"比"免注册试用"更重要。用户注册一次后，长期受益。

## 三、账号隔离技术方案

### 1. 本地数据库隔离

按用户ID隔离IndexedDB数据库：

```
用户A登录 → 使用数据库 JobTrackerDB_userA_id
用户B登录 → 使用数据库 JobTrackerDB_userB_id
退出登录 → 使用默认数据库 JobTrackerDB
```

**实现方式：**
- 登录成功后调用 `switchDatabase(user.id)` 切换数据库
- 退出登录时调用 `switchDatabase(null)` 恢复默认数据库
- 所有数据库操作通过 `getDb()` 动态获取当前实例

### 2. 云端数据隔离

通过Supabase的行级安全策略（RLS）实现：

```sql
-- 每个表都有 user_id 字段
-- RLS策略确保用户只能访问自己的数据
CREATE POLICY "Users can only access their own data"
  ON deliveries FOR ALL
  USING (auth.uid() = user_id);
```

### 3. 同步机制

**自动同步：**
- 操作后5秒内自动加入同步队列
- 同步队列每5秒处理一次，将本地变更推送到云端

**手动同步：**
- 数据管理页面提供"立即同步到云端"按钮
- 提供"从云端恢复"按钮，用于手动触发数据恢复

**登录时自动处理：**
- 本地有数据、云端无数据 → 自动推送到云端
- 云端有数据、本地无数据 → 自动从云端恢复
- 两边都有数据 → 自动双向同步（以本地为准合并）

## 四、用户体验设计

### 1. 登录流程

```
打开网站 → 显示登录页 → 输入邮箱密码 → 登录成功 → 自动同步数据 → 进入首页
```

**未注册账号自动注册：**
- 首次登录时，如果邮箱未注册，自动创建账号
- 减少用户操作步骤

### 2. 退出登录流程

```
点击退出登录 → 确认弹窗 → 退出成功 → 返回登录页
```

**退出时自动处理：**
- 调用 `signOut()` 退出Supabase认证
- 调用 `switchDatabase(null)` 切换回默认数据库
- 清除本地登录状态

### 3. 数据安全提示

登录页底部显示：
> "登录即代表您同意我们的服务条款和数据存储政策"

数据管理页面显示：
> "您已登录账号，数据采用「本地+云端」双存储机制。离线时可正常使用，数据先保存到本地浏览器，联网后 5~10 秒内自动同步到云端。"

## 五、安全性保障

### 1. 密码安全
- 密码通过Supabase Auth进行加密存储（bcrypt）
- 前端不存储用户密码
- 支持忘记密码重置（通过邮箱OTP验证）

### 2. 数据传输安全
- 所有与Supabase的通信通过HTTPS加密
- Supabase提供SSL证书和传输加密

### 3. 数据存储安全
- 云端数据存储在Supabase的PostgreSQL数据库中
- 通过RLS策略确保用户只能访问自己的数据
- Supabase提供定期备份和灾难恢复机制

### 4. 本地数据安全
- 本地数据存储在浏览器的IndexedDB中
- 按账号隔离，不同账号数据互不干扰
- 清除浏览器数据会导致本地数据丢失（但云端仍有备份）
